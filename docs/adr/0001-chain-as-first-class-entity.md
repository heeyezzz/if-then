# 把「链」从 nextRuleId 派生指针迁移成真实体

Status: accepted（设计已定稿，待实现；实现随 Room v7→8 迁移与备份 v7 一起落地）

## 背景

链原本是「不是实体」的设计：数据库只有 `rules` 表，链是顺着每条预案的 `nextRuleId` 指针临时走出来的路径，严格线性、不成环，靠 `Chain.sanitizedNext` 边读边清洗。这套的好处是零冗余、天然防环，但代价是链没有自己的身份——没名字、没 id、没独立生命周期，也就没法改名、没法整条归档、首页一长串成员卡全量铺开显得臃肿。

用户提了两点：链没法折叠太臃肿、链只能新建不能整条删改查。评估下来折叠纯属界面、不必动模型；但整条管理需要链能被寻址。经过逐条盘问，决定把链升成真实体。

## 决策

新增 `chains` 表（`id, name, folderId, status, color, note, createdAt`），`rules` 加 `chainId`（可空）+ `stepIndex`（可空），并**彻底删掉 `nextRuleId`**——不留死列，避免指针和实体两套真相迟早对不上。链成为和散预案同级、直接待在文件夹里的条目。

## Considered Options

- **A：仍用指针模型，只加"整串操作"（折叠 / 删整串 / 移整串 / 清链）**。零迁移、零冗余，覆盖大半诉求。被否：买不到链级身份（名字、单独归档、在列表里当一条东西管），而这些是用户明确要的。
- **C：先只做折叠**。被否：折叠解决的是点1，点2 的整条管理无解，之后还得回来做实体化，不如一步到位。

## 已敲定细则

- 链成员 ≥2 才算一条链；掉到 1 自动散成普通预案（`chainId` 置空）。
- 顺序用整型 `stepIndex`，保存时按行序整条重排；不用分数/间隙序号。
- `folderId` 仍留在每条 `rules` 上（散预案要用）；预案进链后以链的 `folderId` 为准，摘成散预案时把链的夹写回它那一行。链本身成员不各存各的夹。
- 首页：链默认折叠成摘要行（色点+名字+`N 步 · 今日 x/N`+箭头），点开才铺成员卡；打卡只在展开的卡上做，折叠行不放打卡控件。散预案和链混在同一个「预案」列表、共用一套 `sortOrder`。
- 折叠态存本机 DataStore（按 `chainId`），不进备份。`color` 只画链头与竖线。
- 链级操作放首页链头的 ⋯ 菜单（重命名 / 换夹 / 设色 / 归档 / 编辑整串 / 删整串），不新增单独的链条列表页。
- 删整串：每次弹窗让用户选「只拆链，预案和打卡都留」还是「连成员预案带打卡一起删」。
- 从链中间抽走成员（摘出、或被别的链「换已有」抢走）：原链愈合，前后接上。
- 归档链：成员一起退出活动首页和复盘活跃统计，收进文件夹底部「已归档 N」折叠区，可看可撤销；链内成员不单独归档，要归档某一步先摘出。
- 整串编辑页顶部加名字输入框；留空自动拿第一行「如果」当名。一次保存用「已拆开」分多段时，首段用名字框，后面拆出的段自动拿各自链头命名。
- 状态仍只能由用户打卡产生；拖拽排序彻底否决、一律离散点按；左滑快捷区按钮预算已满，新动作放 ⋯ 菜单或弹窗。

## 迁移与备份

- 一次性迁移读旧 `nextRuleId`：顺指针走出路径 → 在每个文件夹边界拆成多段 → 每段建一条链、名取链头「如果」、成员 ≥2 才建、单条退成散预案；`status` 给活动、`color/note` 留空、`createdAt` 取链头预案。
- 备份导出版本升到 v7、带 `chains`；导入只认 v7，旧 v6 直接拒（真机数据靠 Room 就地迁移保住，与备份文件是两回事）。

## Consequences

- 删掉 `Chain` 里成环/破环那套（`wouldCycle`、`sanitizedNext` 的砍边逻辑）：显式成员 + 序号不会再成环，子系统反而简单。
- 首页「折叠」此前是假的——`chainOpen` 只额外开一个整串管理面板，成员卡始终全量竖铺；实体化后才能真正做到把长链收成一行。
- 这是动核心子系统的改造，落地前要先把手机真实数据导一份到非 `/tmp` 的持久位置（`/tmp/recover/ifthen.db` 已随重启丢失），并开 feature 分支，不直接动停在 v0.9 的 main。
